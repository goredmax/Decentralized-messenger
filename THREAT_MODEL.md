# Модель угроз: децентрализованный E2EE-мессенджер

**Версия документа:** 2.0
**Дата:** 2026-09-26

## Статус реализации (прочитайте первым)

Документ описывает модель угроз проекта. Он **не является описанием
текущего состояния кода**. Реализовано и работает:

| Защита | Состояние |
| --- | --- |
| X3DH с проверкой подписи prekey-bundle | Реализовано |
| Проверка подписи handshake инициатора | Реализовано |
| Одноразовость one-time prekey (атомарный `consume`) | Реализовано |
| Double Ratchet, forward secrecy | Реализовано |
| Post-compromise security | Реализовано |
| Откат состояния при неуспешной аутентификации | Реализовано |
| Исключение message keys из сериализации | Реализовано |
| Валидация состояния сессии при загрузке (`DoubleRatchet.from_state`) | Реализовано |
| Примитивы проверены по опубликованным векторам RFC (5869, 7748, 8032) | Реализовано |
| Составные протоколы X3DH / Double Ratchet проверены по векторам | **Невозможно: Signal их не публикует** |
| Соединение X3DH с Double Ratchet (корневой ключ handshake питает ратчет) | Реализовано |
| Associated data сообщения привязывает кадр к сессии | Реализовано |
| Зашифрованное локальное хранилище (scrypt + XChaCha20-Poly1305) | Реализовано |
| Одноразовость ML-KEM-768 prekey | Реализовано |
| Лог прозрачности групповых цепочек | Реализовано, **не** настоящая key transparency |
| MLS (RFC 9420) | Нет кода |

**Не реализовано:**

| Защита | Состояние |
| --- | --- |
| Маршрутизация трафика через Tor, onion services | Нет кода |
| Хранение ключей в OS Keystore | Нет кода |
| Межкадровый padding, обфускация таймингов, cover traffic | Нет кода; негде, пока трафик не пересекает процесс |
| Раздача групповых distribution-сообщений | Нет транспорта между процессами |
| Независимые свидетели / gossip для лога прозрачности | Нет кода; без них это не key transparency |
| Периодическая ротация идентификаторов | Нет кода |
| Panic button, plausible deniability | Нет кода |
| Независимый аудит | Не проводился |

Предыдущая версия этого документа описывала часть перечисленного как
действующую защиту. Это было неверно.

Точная граница возможностей, включая то, что невозможно закрыть кодом в этом
проекте, — в [docs/SECURITY_BOUNDARIES.md](SECURITY_BOUNDARIES.md).

## 1. От кого защищаемся

### 1.1. Провайдер / локальная сеть

**Возможности:** полный доступ к трафику, видит IP, порты, время, объём;
может применять DPI.

**Состояние защиты:** **отсутствует.** Tor-интеграции нет, приложение
подключается к узлам напрямую. Любой трафик, который сегодня производит это ПО,
виден оператору сети.

### 1.2. Глобальный пассивный наблюдатель (GPA)

**Возможности:** корреляция времени входа/выхода из сети, анализ объёмов
трафика на магистралях.

**Состояние защиты:** **частично, и частично по определению.** Длина сообщения
скрыта ступенчатым паддингом (`src/protocol/padding.py`): 1 байт и 5000 байт
дают кадр одинаковой длины, и это измерено, а не заявлено. Не скрыты количество
сообщений, время отправки, направление и собеседник; полная защита от GPA
требует mixnet, которого нет. Обфускация таймингов и cover traffic не
реализованы: негде генерировать шум, пока трафик не пересекает границу процесса.
Mixnet (Nym, Loopix) вышел бы за рамки проекта.

### 1.3. Активный MITM

**Возможности:** подмена ключей, навязывание своих параметров, relay.

**Состояние защиты:** **частично.**

- Подпись signed prekey проверяется инициатором до использования
  (`X3DH.verify_bundle`)
- Инициатор подписывает транскрипт handshake, получатель проверяет подпись и
  берёт identity key из самого транскрипта
- Одноразовость prekey обеспечивается атомарно

**Остаточный риск:** X3DH не защищает от подмены **всего bundle** целиком.
Атакующий, подменяющий и identity key, и signed prekey, образует сессию,
которую жертва считает сессией с настоящим собеседником. Защита от этого —
внеполосная проверка отпечатка ключа (QR-код, safety number), и она **не
реализована**. До её реализации обмен ключами нужно считать неаутентифицированным
на уровне идентичности.

### 1.4. Изъятие устройства

**Возможности:** физический доступ, полный образ файловой системы, brute force.

**Состояние защиты:** **частично.** Приложение шифрует всё, что записывает само:
`src/storage/container.py` — scrypt + XChaCha20-Poly1305, KDF-параметры в
associated data, монотонный epoch. Чего нет: OS Keystore не используется, ключи
лежат рядом с ciphertext в том же контейнере, одноразовость prekey атомарна
только внутри одного процесса (файловых блокировок нет), а подмена контейнера
целиком на более старый валидный не обнаруживается — внешнего якоря epoch нет.
SQLCipher не используется и не нужен: это не SQL.

### 1.5. Спецслужбы

**Возможности:** комбинация вышеперечисленного, 0-day, юридическое давление.

**Состояние защиты:** децентрализация как таковая не даёт защиты, пока нет
P2P-слоя. Слой транспорта существует как интерфейс (`src.p2p.relay.Transport`)
и как relay внутри одного процесса, но ни один кадр не пересекает границу
процесса: два клиента на двух машинах не существуют. Отсутствие идентификаторов
(телефон, email) в криптографии закладывается, но не реализовано на уровне
протокола.

## 2. Что защищаем

### 2.1. Содержание сообщений

**Гарантия:** E2EE при условии, что получатель получил корректный bundle от
доверенного источника. Механизм: X3DH → root key → Double Ratchet,
XChaCha20-Poly1305 с заголовком в associated data.

### 2.2. Метаданные

**Состояние:** **не защищены.** Ничего из заявленного (Tor, padding, ротация
идентификаторов, отсутствие логов соединений) не реализовано. Скрытие
социального графа не обеспечено.

### 2.3. Идентичность

**Механизм:** идентификатор — публичный ключ Ed25519. Onion-адрес из ключа **не
реализован**.

**Оговорка:** один ключ используется и для подписи, и для DH (конверсия
Ed25519 → X25519), в отличие от спецификации Signal, где ключи раздельны.
Компрометация identity key означает компрометацию обеих ролей.

## 3. Чего не защищаем

### 3.1. Компрометация ОС

Keylogger, screen recorder, RAT. Не защищается приложением. Нужны Tails, Qubes
или аналог.

### 3.2. Принуждение к раскрытию

Планировались panic button и plausible deniability. **Не реализованы.**

### 3.3. Глобальная корреляция трафика

Tor уменьшает риск, но не устраняет; нужен mixnet. В текущем коде не заявлен и
не реализован даже Tor.

### 3.4. Side-channel атаки

Используются constant-time примитивы libsodium для DH и AEAD. Полная защита от
аппаратных side-channel на уровне приложения невозможна. Сравнения в коде
(`hmac.compare_digest` для сравнения публичных значений, проверки счётчиков) не
являются constant-time по отношению к секретам, и модель не заявляет такой
защиты.

### 3.5. Квантовый противник, у которого сломана и ML-KEM

**Состояние:** частично закрыто, полностью — нет. `src/crypto/pq.py` добавляет
вклад ML-KEM-768 в корневой ключ X3DH, поэтому трафик, записанный сегодня,
останется непрочитанным после появления практического взлома X25519: собрав
материал handshake'ей, атакующий не восстановит ML-KEM-секрет.

Противник, у которого сломана и ML-KEM, защиты не получает: ML-KEM-768
считается безопасным, но не является доказанным. Смена параметров потребует
новой версии протокола и, скорее всего, миграции identity key.

**Не покрывается:** подмена всего bundle. Атакующий, заменивший identity key
вместе с signed prekey, проходит все проверки, включая постквантовые, и
получает сессию вместо настоящего собеседника. Единственная защита —
сравнение safety numbers вне контроля атакующего.

**Стоимость:** 1184 байт в каждом prekey bundle и 1088 байт в каждом handshake.
Bundle вырос примерно в десять раз.

## 4. Резюме

| Угроза | Реализация | Стратегия |
| --- | --- | --- |
| Перехват трафика провайдером | Нет | Требуется Tor |
| Анализ метаданных (GPA) | Нет | Требуется mixnet либо хотя бы Tor |
| Длина отдельного сообщения | **Да** | Ступенчатый паддинг, пол 8192 байт |
| Активный MITM (частичная подмена) | **Да** | Проверка подписей X3DH |
| Подмена identity key целиком | Нет | Нужна внеполосная проверка отпечатка |
| Повторное использование prekey | **Да** | Атомарный `consume`, у X25519 и у ML-KEM |
| Откат групповой цепочки на скомпрометированную | **Частично** | Лог ловит повтор доверенной цепочки; не ловит лог, переставший расти |
| Подмена истории лога двум участникам (форк) | **Да** | Hash-linked лог, подпись отправителя |
| Квантовый противник, сломавший X25519 | **Да** | ML-KEM-768 в корневом ключе |
| Квантовый противник, сломавший ML-KEM | Нет | Требуется гибридизация или смена параметров |
| Изъятие устройства | Частично | scrypt + AEAD контейнеры; нужен OS Keystore |
| Компрометация ОС | Нет | Требуется безопасная ОС |
| Принуждение к раскрытию | Нет | Panic button не реализован |
| Независимый аудит | Нет | Требуется |
