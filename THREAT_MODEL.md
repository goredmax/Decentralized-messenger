# Модель угроз: децентрализованный E2EE-мессенджер

**Версия документа:** 2.0
**Дата:** 2026-09-26

## Статус реализации (прочитайте первым)

Документ описывает модель угроз проекта. Он **не является описанием
текущего состояния кода**. Реализовано и работает:

| Защита | Состояние |
| --- | --- |
| X3DH с проверкой подписи prekey-bundle | Реализовано |
| Проверка подписи handshake инициатора | Реализовано |
| Одноразовость one-time prekey (атомарный `consume`) | Реализовано |
| Double Ratchet, forward secrecy | Реализовано |
| Post-compromise security | Реализовано |
| Откат состояния при неуспешной аутентификации | Реализовано |
| Исключение message keys из сериализации | Реализовано |
| Валидация состояния сессии при загрузке (`DoubleRatchet.from_state`) | Реализовано |

**Не реализовано:**

| Защита | Состояние |

| Зашифрованное локальное хранилище (SQLCipher) | Нет кода |
| Хранение ключей в OS Keystore | Нет кода |

## 1. От кого защищаемся

### 1.1. Провайдер / локальная сеть

**Возможности:** полный доступ к трафику, видит IP, порты, время, объём;
может применять DPI.

**Состояние защиты:** **отсутствует.** Tor-интеграции нет, приложение
подключается к узлам напрямую. Любой трафик, который сегодня производит это ПО,
виден оператору сети.

### 1.2. Глобальный пассивный наблюдатель (GPA)

**Возможности:** корреляция времени входа/выхода из сети, анализ объёмов
трафика на магистралях.

**Состояние защиты:** **отсутствует.** Заявленные в README padding, обфускация
таймингов и cover traffic не реализованы. Полная защита от GPA требует mixnet
(Nym, Loopix), что выходит за рамки проекта.

### 1.3. Активный MITM

**Возможности:** подмена ключей, навязывание своих параметров, relay.

**Состояние защиты:** **частично.**

- Подпись signed prekey проверяется инициатором до использования
  (`X3DH.verify_bundle`)
- Инициатор подписывает транскрипт handshake, получатель проверяет подпись и
  берёт identity key из самого транскрипта
- Одноразовость prekey обеспечивается атомарно

**Остаточный риск:** X3DH не защищает от подмены **всего bundle** целиком.
Атакующий, подменяющий и identity key, и signed prekey, образует сессию,
которую жертва считает сессией с настоящим собеседником. Защита от этого —
внеполосная проверка отпечатка ключа (QR-код, safety number), и она **не
реализована**. До её реализации обмен ключами нужно считать неаутентифицированным
на уровне идентичности.

### 1.4. Изъятие устройства

**Возможности:** физический доступ, полный образ файловой системы, brute force.

**Состояние защиты:** **отсутствует.** Хранилища нет, SQLCipher не подключён,
OS Keystore не используется. Всё, что приложение записывает на диск, лежит
без шифрования приложением.

### 1.5. Спецслужбы

**Возможности:** комбинация вышеперечисленного, 0-day, юридическое давление.

**Состояние защиты:** декентрализация как таковая не даёт защиты, пока нет
P2P-слоя. Отсутствие идентификаторов (телефон, email) в криптографии
закладывается, но не реализовано на уровне протокола.

## 2. Что защищаем

### 2.1. Содержание сообщений

**Гарантия:** E2EE при условии, что получатель получил корректный bundle от
доверенного источника. Механизм: X3DH → root key → Double Ratchet,
XChaCha20-Poly1305 с заголовком в associated data.

### 2.2. Метаданные

**Состояние:** **не защищены.** Ничего из заявленного (Tor, padding, ротация
идентификаторов, отсутствие логов соединений) не реализовано. Скрытие
социального графа не обеспечено.

### 2.3. Идентичность

**Механизм:** идентификатор — публичный ключ Ed25519. Onion-адрес из ключа **не
реализован**.

**Оговорка:** один ключ используется и для подписи, и для DH (конверсия
Ed25519 → X25519), в отличие от спецификации Signal, где ключи раздельны.
Компрометация identity key означает компрометацию обеих ролей.

## 3. Чего не защищаем

### 3.1. Компрометация ОС

Keylogger, screen recorder, RAT. Не защищается приложением. Нужны Tails, Qubes
или аналог.

### 3.2. Принуждение к раскрытию

Планировались panic button и plausible deniability. **Не реализованы.**

### 3.3. Глобальная корреляция трафика

Tor уменьшает риск, но не устраняет; нужен mixnet. В текущем коде не заявлен и
не реализован даже Tor.

### 3.4. Side-channel атаки

Используются constant-time примитивы libsodium для DH и AEAD. Полная защита от
аппаратных side-channel на уровне приложения невозможна. Сравнения в коде
(`hmac.compare_digest` для сравнения публичных значений, проверки счётчиков) не
являются constant-time по отношению к секретам, и модель не заявляет такой
защиты.

## 4. Резюме

| Угроза | Реализация | Стратегия |
| --- | --- | --- |
| Перехват трафика провайдером | Нет | Требуется Tor |
| Анализ метаданных (GPA) | Нет | Требуется mixnet либо хотя бы Tor |
| Активный MITM (частичная подмена) | **Да** | Проверка подписей X3DH |
| Подмена identity key целиком | Нет | Нужна внеполосная проверка отпечатка |
| Повторное использование prekey | **Да** | Атомарный `consume` |
| Изъятие устройства | Нет | Требуется SQLCipher + Keystore |
| Компрометация ОС | Нет | Требуется безопасная ОС |
| Принуждение к раскрытию | Нет | Panic button не реализован |
| Независимый аудит | Нет | Требуется |
