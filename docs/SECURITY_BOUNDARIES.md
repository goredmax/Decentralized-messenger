# Границы возможностей: что защищено, а что нет

Документ отвечает на вопрос «насколько это безопасно» не общими словами, а
по пунктам. Каждое утверждение здесь либо покрыто тестом, либо помечено как
непроверенное.

Проверено на момент написания: **392 теста проходят**, bandit не находит
замечаний, pyflakes чист.

---

## 1. Реализовано и проверено

| Механизм | Что покрывает | Чем проверяется |
| --- | --- | --- |
| X3DH с проверкой подписи bundle | Аутентификация связи identity key ↔ signed prekey. Активный MITM, подменяющий signed prekey, отвергается | `test_x3dh_mitm.py` |
| Подпись handshake (транскрипт) | Аутентификация инициатора. Ответчик берёт identity key из самого транскрипта, а не от вызывающего | `test_x3dh_mitm.py` |
| Одноразовость one-time prekey | Атомарный `consume`. Replay сжигает forward secrecy, поэтому handshake прерывается | `test_prekey_store.py`, гонка 12 потоков |
| Double Ratchet | Forward secrecy, post-compromise security | `test_double_ratchet.py` |
| Откат состояния при отказе | Битый пакет не рассинхронизирует сессию, подделанный заголовок не проворачивает root key | `test_double_ratchet.py` |

| Ротация signed prekey | `signed_prekey_id` + `minimum_signed_prekey_id` позволяют списать устаревший bundle | `test_rotation.py` |
| Громкий отказ при пустом пуле | 3-DH без forward secrecy требует явного opt-in | `test_rotation.py` |
| Safety numbers | Внеполосная верификация против подмены всего bundle | `test_verifier.py` |
| Шифрование хранилища | scrypt + XChaCha20-Poly1305, KDF-параметры в associated data, epoch | `test_storage.py` |
| Wire-формат | Тотальные декодеры, каноничные varint, лимиты длины | `test_wire.py`, 3000 случайных блобов |
| Вектора RFC | HKDF (RFC 5869), X25519 (RFC 7748) | `test_vectors.py` |

## 2. Чего эти механизмы НЕ делают

Это важнее предыдущего раздела.

**X3DH не защищает от подмены всего bundle.** Атакующий заменяет identity key
*и* signed prekey, подписывая замену своим ключом. Bundle проходит проверку
идеально, инициатор оказывается в настоящей зашифрованной сессии не с тем
человеком. Единственная защита — safety numbers, и они работают только если
сравнение идёт по каналу вне контроля атакующего. **Автоматической проверки
идентичности нет.**

**Safety numbers не защищают, если канал скомпрометирован.** Если злоумышленник
контролирует канал сравнения, сравнение бесполезно. Это свойство метода, а не
дефект реализации.

**Одноразовый prekey не спасает от повторного использования базы.** Гарантия
одноразовости обеспечивается в пределах одного процесса. Между процессами не
работает: нет файловых блокировок. См. `src/storage/store.py`.

**Double Ratchet не скрывает метаданные.** Видны моменты отправки, размеры,
частота, собеседник по адресу. Ничего из этого не шифруется.

**Шифрование хранилища не спасает от подмены файла целиком.** Атакующий,
заменивший файл на более старый, но внутренне валидный, не будет обнаружен:
внешнего якоря epoch нет. `load(minimum_epoch=...)` существует для вызывающего,
у которого якорь есть.

## 3. Карта констант-тайма

| Место | Свойство |
| --- | --- |
| X25519 (`crypto_scalarmult`) | Констант-тайм, libsodium |
| XChaCha20-Poly1305 | Констант-тайм, libsodium |
| Сравнение подписей, `compare_digest` | Констант-тайм |
| Сравнение confirmation MAC, `compare_digest` | Констант-тайм |
| Сравнение `identity_key_x25519` при декодировании, `compare_digest` | Констант-тайм |
| Сравнение remote DH в ратчете, `compare_digest` | Констант-тайм |
| Поиск в `skipped_keys` (dict по `(dh, n)`) | **Не констант-тайм.** Ключи — публичные: DH-ключ в заголовке открыт, номер сообщения тоже |
| Сравнения счётчиков `Nr`/`Ns`/`PN` | **Не констант-тайм.** Значения публичны: они передаются в заголовке или выводятся из публичных номеров |
| Сравнение `n` для duplicate/replay | **Не констант-тайм.** Номер сообщения публичен |
| Safety numbers, сравнение цифр | **Не констант-тайм, и это нормально.** Число публично: его читают вслух |

Вывод: не-констант-тайм места оперируют **публичными** значениями. Утечки
секрета там нет. Это осознанный компромисс, а не недосмотр.

## 4. Обнуление памяти

**Что есть:** `src.crypto.key_management` и `src.storage.container` работают с
`bytes`. PyNaCl даёт `sodium_memzero` для `bytearray`, но код его не вызывает.

**Чего нет:** гарантированного стирания ключевого материа. В Python строки и
`bytes` иммутабельны, GC копирует объекты произвольно, и «стереть» ключ
невозможно — можно лишь стереть конкретный известный буфер.

**Что можно сделать без переписывания:** перевести ключевой материал в
`bytearray` и вызывать `sodium_memzero` при закрытии сессии. Это улучшит
положение, но копии, сделанные интерпретатором, останутся.

**Настоящее решение:** ядро криптографии на Rust с крейтами `zeroize` и
`secrecy`, выставленное через PyO3. Достижим уровень native-кода. Это отдельный
проект.

**Не заявляется:** защита от дампа памяти, swap, hibernation-файлов и core dump.

## 5. Что упирается в отсутствующий сетевой слой

Транспорта нет вообще. Два клиента не могут обменяться сообщениями, потому что
нечем. Из этого следует, что **невозможно реализовать** — не сложно, а именно
невозможно в текущем состоянии кода:

- **Cover traffic** — негде генерировать шум, если трафика нет
- **Обфускация таймингов** — нечего обфусцировать
- **Защита от глобальной корреляции** (GPA) — нет сетевого пути
- **Mixnet** (Nym, Loopix) — большой отдельный проект
- **Tor, onion services, circuit management** — нет ни кода, ни зависимостей
- **Padding межкадровый** — длина ciphertext паддится, но длина кадра и
  тайминги остаются

Порядок здесь один: сначала транспорт, потом метаданные. Пропустив первый шаг,
второй бесполезен.

## 6. Чего нет по протоколу

- **Group messaging (Sender Keys)** — не реализован
- **Внеполосная верификация встроена** как числа, но нет UI, QR и сценария
  «сравни перед тем, как писать» в коде вызывающего
- **Автоматического уведомления peer'ов о ротации** нет: `rotate()` инвалидирует
  старый bundle только для того, кто знает новый `signed_prekey_id`
- **Property-based тестов** на ратчет нет, только примеры
- **Интеграционного теста между процессами** нет
- **Клиента (CLI/UI)** нет
- **Аудита X3DH против официальных векторов Signal нет и невозможно** —
  реализация использует Ed25519 с конверсией в X25519, тогда как спецификация
  предполагает нативный curve25519 identity key. Дагисты не совпадут в
  принципе. Заявлять такую проверку было бы ложью. Применимые вектора
  (HKDF, X25519, Double Ratchet) подключены

---

## 7. Чего не может код

**Независимый аудит.** Никакой тест не заменяет ревьюера. Правки в этом
репозитории вносил тот же процесс, который их проверял, поэтому они не являются
аудитом и не могут им считаться.

**Доверие к корню.** Ключи генерируются локально, но доверие к ним основано на
том, что скомпрометированной сборочной среды нет. Воспроизводимость сборки
обеспечена (`requirements.lock` с хешами, `pip install --require-hashes`),
но это не защита от подмены зависимости до её попадания в lock.

**Соответствие стандартам.** Отклонения от спецификации Signal задокументированы
в `README.md`: непустой context string в HKDF `info`, объединённая роль
Ed25519/X25519 ключа, собственный формат safety numbers. Ключи **не**
совместимы с libsignal.
